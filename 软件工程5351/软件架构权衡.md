# 软件架构权衡

架构决策**本质上都是权衡**（tradeoff）：质量属性（quality attributes）之间经常互相冲突，无法同时最优，只能挑一个 **primary driver**，并**明说被牺牲的那个 concern**（losing quality concern）。质量属性用**质量场景**（quality scenario）表达，形式与需求工程里的 quality requirement 一致：stimulus / environment / response / measure——必须可度量，否则无法确认。

决策用 **ADR（Architecture Decision Record）**记录，结构为 context → options → decision → consequences → status → confirmation + owner。要点在于 consequences 要写三层：**improves**（改善了谁）、**adds**（引入了什么新负担/新失败模式）、**does not establish**（本决策**不**证明什么）。最后必须有具名 owner 与确认证据（confirmation），并把未执行的部分诚实地标成 "planned, not executed"。

Week 5 studio 用一个具体案例把权衡讲清：为课程做一个 **AI-assisted deadline coach（CampusFlow）**——显示授权截止日期、给紧急任务排序、解释排序并发送可选提醒。架构压力在于：course data、preferences、模型输入、tool calls 与外部分别跨越不同的 **trust boundary 与 failure boundary**。核心风险假设：**若架构让模型输出直接触达授权课程数据或直接执行工具，则 privacy 与 availability 可能失效**——因为一个不可信组件坐到了 deadline view 的关键路径上，provider timeout、错误的 ranking 或越界 tool call 都会阻断、污染或泄漏权威列表。

四类质量场景（指标均为 classroom 假设、planned check 未执行）：**Performance**——正常课堂负载下打开截止列表应立即显示、ranking 在 2 秒内返回且 ≥95% 请求达标；**Privacy**——当模型输出或 prompt 组装涉及最小排序字段之外的任何字段（他人记录、凭证、自由文本历史）时，系统应在调用 provider 前拒绝并脱敏，并记录该拒绝；**Availability**——当 model/notification provider 超时、拒绝十分钟后恢复时，系统应继续从 snapshot 提供授权截止列表并显示明确的 ranking-unavailable 状态，核心视图**永不阻塞**；**Modifiability**——更换模型 provider 时只改 gateway 实现与配置，deadline view、授权逻辑、course-data adapter 不动。

**Primary driver 选了 privacy**，理由：模型在 trust boundary 之外却能对授权数据提出动作，而 privacy 失败**发布后无法修复**，慢一点只是性能问题，可以接受；被牺牲的是 performance——有界确认、schema validation、deny-by-default 的再授权都会给 ranking 增加延迟，之所以可接受，是因为即便没有任何 ranking，授权截止列表依然可用。

被选方案是 **Option B**：Coach API 持有授权 snapshot，以有界预算与 schema validation 调模型 gateway，视图渲染 snapshot，把 ranking 当作可选增强；备选 A（web app 直接调数据源与模型）组件最少却把凭证与 provider 可用性放上关键路径，C（模型 gateway 把 ranking 写回 snapshot）给不可信组件开了对授权数据的写路径。ADR-02 在"failure pack"压力下加固：R1 核心路径保留 + 超时有明确的 ranking-unavailable；R2 freshness 暴露——每项带 source 与 last-updated，无法确认当前的标记为 stale 且绝不按 current 样式呈现；R3 通知隔离——outbound-only、allow-list，provider 拒绝只标记单条失败；R4 tool authority 有界——gateway 只能"提议"tool call，action broker 按授权范围 deny-by-default 地再授权。Rollback 是关掉 ranking 与 alerts、只提供未排序的授权列表。

真正可迁移的心得：**组件图在没有写明职责、trade-off 与 confirmation 之前只是一份 proposal**；把 driver→option→consequence→confirmation→owner 这条决策链显式化；区分"已测量"与"planned/unverified"，**不把残留风险（residual risk）伪装成证据**。这套权衡视角与 Week 4 stakeholder negotiation 里的冲突同源——product owner 想要"尽快发布"，而 privacy/accessibility 要求压过速度，最终决策必须写出证据、losing concern 与 unresolved limitation。
