# 软件过程模型

为什么需要**软件过程模型**（software process model）？讲义用一个动机例子把问题讲透：设两个能力强、投入的程序员 A、B，A 负责代码 P、B 负责代码 Q，彼此能满足对方需求、还能随时找用户 U 确认需求——这是"完美场景"（a perfect case）。现实中恰恰相反：A、B 对各自代码的了解是**逐渐**建立（gradually）的，交付的是有 bug、功能不全的版本；B 对 P 的需求会随自己对 Q 的理解而变化（requirement changes over time）；人员流动更致命——一个月内 A 走、A1 补位、B 走、B1 补位，七个月后 A2 只能沿 A→A1→B1→A2 的链条间接了解 P 的需求，而每个经手人都想**最小化**交接工作量，用户 U（例如房产中介）更不愿被打扰，交接只是"副业"。当项目足够大，没有人掌握全部细节，指望"拿到清晰任务书再动手"并不现实。

因此需要一个**过程模型**：一组 (1) activities、(2) techniques、(3) deliverables、(4) tools，配合 (5) best practices（如 pair programming、agile），让工程师与 PM 管理软件系统。目标是：以可控的任务顺序降低开销、提升信息传递效率、让交付对用户期望可追踪（traceability）、可预测与追踪任务完成度和遗留问题、提升代码质量。现实数据支撑这个需求：常见项目 89% 超预算，按时按预算者仅实现 42% 原始需求；Standish CHAOS 2020 报告 66% 项目部分或完全失败，大项目成功率 10%、小项目 90%。

常见活动：收集需求、设计、编码、测试、部署、维护、配置管理、项目管理。组织方式不同 → 不同模型：

- **Waterfall**：每个活动完全产出全部 deliverables 后才进入下一活动。工作流简单，但要求同时对照 design、coding 细节与 requirements 来测试，且制造"阶段清晰可分"的假象；上游错误修复代价极高（越早验证越便宜）。
- **V-Shape Waterfall**：每阶段有对应 validation target（需求→验收测试、设计→系统测试、编码→单元/集成测试），强调阶段式验证。
- **Prototyping**：先写代码、后补设计/需求文档；原型可能含 bug、只实现部分功能或仅界面效果，让用户更容易"指出"需求，在正式设计前增量获取并验证需求。
- **Incremental**：把需求拆成子集，v1 实现一个子集，v2 在其上叠加，逐步扩大需求集合。
- **Spiral**：融合 waterfall、prototype、incremental 且更系统，核心是 plan → 原型 → 修订计划，通过迭代认识对象，强调风险。
- **Unified Process (UP)**：同一迭代中各类活动并行。

贯穿各模型的教训：能尽早验证的产物应尽早验证，修复成本随阶段后移急剧上升；宁可要一个"优雅降级的子系统"，也不要最后什么都没有。选模型看**风险与反馈**：需求稳定、变更代价高 → plan-driven；需求不确定、实验便宜 → 短迭代；后果严重且不确定 → 显式风险评审。关键认识：**过程模型是一种控制策略，不是项目身份**；Agile 也不等于不计划，只是把计划变成短周期、可检验的假设。
