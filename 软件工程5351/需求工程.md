# 需求工程

讲义用一句话点出问题的本质：**"As a customer, I want to buy PS5 from the website."** 这条是 functional 且 verifiable 的需求，开发团队会以为交付它用户就满意了。但远远不够——如果每次点击或每个输入框要等 30 分钟（efficiency issue），或网站同一时刻只允许一个顾客买一件商品（scalability issue），需求照样失败。所以**必须知道需求的 non-functional 部分**。

**功能性需求**（functional requirements）说系统**必须做什么**；**质量/非功能性需求**（quality / non-functional requirements）约束它**做得多好**。术语很混乱：同一个东西在不同领域被叫作 system properties、quality attributes、constraints、non-behavioral requirements、goals、extra-functional requirements 等。很多项目里非功能需求占全部需求的比例很高。关键判断：**一个质量属性若不可度量、不可验证，我们无从预测软件满足它的程度，只能依赖用户的主观评价**——这正是要把它写"可验证"的原因。

**需求工程（RE）**是找出并组织功能性/非功能性需求的过程，产物是 **requirements specification**——它既是给客户的 contract，也是设计的起点。RE 是一个**迭代**过程，含四大步：

1. **Elicitation（理解问题）**——从各来源收集需求。
2. **Specification（描述问题）**——把需求结构化地写下来。
3. **Validation（就问题的性质达成一致）**——确认需求正确、完整、一致等。
4. **Negotiation（就问题的边界达成一致）**——在利益相关者之间消解冲突。

**需求获取（elicitation）**本身含五个迭代步骤：理解应用领域（含政治、组织、社会层面的约束）；识别需求来源（人：stakeholders、users、SME；物：现有系统、操作流程、文档/手册/表格）；分析利益相关者（内外部群体、客户与直接用户，识别 key user representatives 与 product champions）；选择合适的技术与工具；实际执行获取。常用技术：interview（unstructured / structured / semi-structured；structured 的成功取决于知道该问什么、何时问、谁来答，可用 Volere 模板）、brainstorming、task analysis、scenario-based analysis、form analysis、focus group、facilitated workshop、mind mapping、group storytelling、user stories；问卷被专家认为**不有效**。

**可验证性**落在"quality requirement 就是一个可测试的场景"上，用固定形式描述：**source（谁/什么触发）、stimulus（刺激）、environment（环境）、response（系统应做什么）、response measure（度量）**。把 "reliable" 这类词翻译成可观察的界限（例如"95% 的请求在 2 秒内返回"），否则无法验证。功能需求与质量需求都需要 owner、rationale 与 verification evidence。

RE 常见错误（IEEE 论文总结）：noise（无关信息）、silence（问题里存在却未写进规格的特性）、over-specification（讲方案而非问题）、contradictions、ambiguity、forward references、wishful thinking（不现实的特性）。自然语言规格很危险，例如 "All users have the same control field" 至少三义：同一个值？同一种格式？只有一个字段？因此需要 validation：对规格做 correctness、completeness、consistency、accuracy、readability、testability 检查；同一需求来自多个来源时更易推理其有效性（但别过度依赖间接来源/intermediary）。

**协商与优先级**：需求不只需要获取，还要在 elicitation 与 prioritization 两处与利益相关者协商。常用 **MoSCoW**：Must haves（强制）、Should haves（重要非强制）、Could haves（有余力才做）、Won't haves（这次不做）。结构化时可按层级（高层需求分解为低层）并把需求关联到特定利益相关者。实战做法（Week 4 stakeholder lab）：先画利益相关者地图（用户、操作者、购买者、维护者、受影响方），标出冲突与**缺席的声音**（"某方没参会"不等于其约束消失）；用能产出证据的访谈问题（覆盖现状、异常路径、度量、trade-off、证据 owner）；写功能需求 + 质量约束 + 验收标准（Given/When/Then）+ 一个仍需证据的显式假设；协商时明说 losing concern 与 unresolved limitation，不把偏好或假设悄悄变成需求。
