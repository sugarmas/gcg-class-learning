# 现代代码评审

**代码评审**（code review）是"由作者以外的开发者对源代码做人工检查（human inspection）"。目的是维护并促进 source code quality，同时通过设计方案与实现方案的**知识转移**（knowledge transfer）维系开发社区。关键认识：找 bug 只是众多目的之一——还有 code improvement、alternative solution、knowledge transfer、team building 等。

按正式程度分三档：

- **Code walkthrough**：非正式会议，作者带团队过一遍自己的代码。作者与评审者不是同一人时更有效；常与 pair programming 结合。与测试找 bug 的效果相近，但更耗人力，故更不经济。
- **Code Inspection**（Fagan inspection）：高度结构化的正式流程，公司里也叫 static testing。会前作者教育评审者、评审者以测试视角读代码；会中逐行走过并用 checklist 检查，评审者会前分配焦点角色，靠"在脑中执行代码"找错；会后作者修正、moderator 验证。特征是 formal、synchronous、heavy-weighted，工具支持是次要的。适合找 bug 与发现流程改进点，但已日渐式微。
- **Modern Code Review (MCR)**：**轻量、工具化、异步**、只评审代码**变更（patch / delta）而非整份代码**——这是当代主流。流程：作者 A 针对代码块 C 做补丁 P 解决某些问题，经电子渠道（email、WhatsApp、WeChat 或 GitHub 工具）发给评审者集合 R；每位 R 判定 P 好坏；A 提交 P，其余人可做 post-commit review。特点是 informal（无预定义角色）、tool-based（GitHub、Gerrit、ReviewBoard、Phabricator）、asynchronous、聚焦 patch。

**评审什么/不评审什么**：MCR 承接了 inspection 的 moderator 式 **gate-keeping**，但范围更广——成员级问题解决、可读性、可维护性、遵循公司规范、防止意外。注意：代码评审**不适合发现安全 bug**（Thompson & Wagner 2017 的大规模研究结论），安全需专门的 threat modeling 与 trust boundary 分析。测试代码也**应**被 review，但侧重点不同、频率更低（通常随生产代码一起）。工业案例（Xerox）显示：应对糟糕的设计与 coding style 是重构的主要驱动，而功能变更与修 bug 也常触发重构。

**有效性与最佳实践**：当代 peer review 遵循轻量、灵活的流程——尽早（提交前）、及时、频繁评审；评审者**事先了解上下文和代码**时审得更快、反馈更有价值；改动要小；评审者 1~5 人。Google 的数据：评审频率中位数每周 4 小时 / 4 次评审；作者等待 1~5 小时；改动规模 1 行代码占约 10%、单文件约 30%、少于 10 文件约 90%。用 round-robin 轮流指派评审者以免**总是压榨最强的几个人**；用 style checker / 静态分析（如 Java 的 Checkstyle）补充人工评审。

常见问题与反模式：高复杂度代码得到的讨论与反馈反而**更少**，而反馈少的代码发布后 bug 更多；距离（地理、组织/跨团队）导致延迟与误解；社交因素——语气负面（negative tone）的评论用处更小，作者对"被要求改评价"不满；上下文错配（"锦上添花" vs 紧急修复、完整方案 vs 高层草图）造成误解。还有一点反直觉：没有证据表明多做几轮 MCR 能提升开发者的代码质量。

作为**可问责的决策**：review 的正式程度应随风险而变（高风险改动需要明确 owner、检查与证据，低风险可轻量但不可不审）；一个 pull request 讲一个连贯的 change，无关重构/格式化/行为变更分开；PR 描述要带证据（为什么、改了什么行为、跑了哪些检查与残留局限）；merge gate 要显式（approval、tests、policy findings 回答不同问题）；评论要 actionable（指向位置、后果、可检验的修订）；AI 评审只是 signal 不是 approval，AI 生成的改动要过同样的证据与问责闸门，永远不能自审自并。
